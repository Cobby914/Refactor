# ScaleSense co-simulation v2 architecture

## Simulator authority

Use one coordinator for synchronous traffic and rendering. SUMO owns the behavior and lifecycle of simulated vehicles, bicycles and pedestrians. CARLA owns rendering, sensors and frame IDs. The existing fused scenarios use a fixed roadside rig and SUMO-controlled traffic, so a one-way actor mirror covers their requirements. Revisit bidirectional synchronization if a future scenario needs a CARLA-controlled vehicle to affect SUMO traffic. Continue to support CARLA-only dataset collection through its existing entry point.

Each coordinator iteration advances SUMO once, runs the existing scenario controller and reconciles actor lifecycle, transforms and traffic signals, then advances CARLA once. Apply CARLA commands with acknowledgement and with the batch tick flag disabled. Keep the CARLA frame ID and SUMO time together. Associate the exact CARLA world snapshot with this frame, then let sensor callbacks deliver independently. The campaign can use the first completed paired step as its recording anchor.

The compatibility target is CARLA 0.9.16 with SUMO and TraCI 1.28.0. The CARLA tag and ScenarioRunner release match the CARLA target. ## First increment

[`fusion.simulation_engine`](../../fusion/simulation_engine.py) contains the ordered step controller. The owning session provides the initial CARLA frame and SUMO time after setup, the fixed step length, and operations to advance SUMO, synchronize traffic and tick CARLA. One successful call returns an immutable step index, SUMO time and CARLA frame ID. A discontinuity or a failed operation invalidates the session. An RPC timeout can occur after an operation has already taken effect, so the lifecycle owner must tear down the session and start a fresh one using new baselines. The engine returns after the CARLA tick and contains no sensor waits.

## Live traffic session

[`fusion.traffic_session`](../../fusion/traffic_session.py) runs the engine on the bundled Town10HD_Opt scenarios. It builds files in a run-scoped temporary directory, checks the radar spawn-exclusion rule and uses one headless SUMO child. The [SUMO adapter](../../fusion/sumo_adapter.py) establishes a private TraCI connection, queries the effective timestep, and tracks and reaps its child even if initialization fails. A connection-scoped socket timeout bounds TraCI reads. TraCI 1.28 exposes this socket through a private field, so retest that behavior when upgrading TraCI.

The [CARLA adapter](../../fusion/carla_adapter.py) requires a dedicated, idle `Town10HD_Opt` endpoint. It checks the client/server build identifiers and rejects a world already in synchronous mode. After taking a copy of the world settings, it applies and verifies synchronous mode and the effective SUMO timestep. CARLA can tick internally while it applies a new fixed delta, so the engine samples its frame origin after settings settle. Each subsequent tick checks the returned frame against its world snapshot and verifies the actual delta. [CARLA 0.9.16 implementation](https://github.com/carla-simulator/carla/blob/0.9.16/LibCarla/source/carla/client/World.cpp)

The session restores the saved CARLA settings on normal completion, startup errors and handled interrupts. It then closes TraCI and waits for the specific SUMO child, killing it if it exceeds the grace period. A hard-killed coordinator can still leave CARLA synchronous and requires recovery on that endpoint. Setup and stepping require exclusive access to the CARLA clock.

## Scenario, actor and signal synchronization

- The v2 process passes its private TraCI connection to the existing scenario controllers, bus setup and corridor signal program. It reuses the existing SUMO routes, controller policies, CARLA blueprint mappings and Town10HD transforms, including junction height and sidewalk placement. Legacy entry points use their usual connections.
- The [actor registry](../../fusion/actor_mirror.py) maps actor kind and SUMO ID to the current CARLA ID. Bicycles are SUMO vehicles with bike blueprints. The registry reconciles actors in stable order, and walker blueprints are selected from a sorted list using a seed and stable hash. A cull or SUMO arrival releases the mirror. Re-entry creates a new CARLA ID for the same SUMO identity.
- The mirror waits for CARLA spawn, transform, physics and destroy batch responses with tick cues disabled. It retries spawn collisions at the existing bounded height offsets, defers crowded spawns and reports their count. It records ownership as soon as a spawn is acknowledged. When a response is lost, teardown can refresh the world state and identify committed spawns by their session tag. Cleanup targets only registry IDs and that tag.
- The [signal adapter](../../fusion/traffic_light_mirror.py) maps ten physical signal heads to directed SUMO approaches at junctions 189, 532 and 719. At startup it checks the CARLA signal group and the proximity of each stop waypoint to its SUMO approach. CARLA landmark 951 uses SUMO approach 15, near the CARLA stop waypoints on road 16. Each physical head represents an approach aspect. Links that can have protected green drive the aspect where present, so a permissive turn does not turn a red through-signal green. Separate turn arrows and pedestrian signal heads are outside this mapping.
- CARLA 0.9.16 exposes asynchronous signal setters and freezes lights globally. The dedicated session pauses all CARLA lights, sends mapped aspects before each paired tick, and verifies them from that tick before exposing its frame. Setup and teardown can use bounded maintenance ticks outside the paired frame sequence. Teardown restores saved corridor aspects and the prior freeze mode. CARLA resumes signal timing from its own controller state. [CARLA 0.9.16 signal implementation](https://raw.githubusercontent.com/carla-simulator/carla/0.9.16/LibCarla/source/carla/client/TrafficLight.cpp)

The dataset CLI and GUI use the legacy implementation while v2 gains capture support.

## Next interfaces and remaining decisions

- The lifecycle manager owns the rig, world settings, Traffic Manager state, TraCI connection and SUMO child. It starts cleanup with the first successful resource acquisition, tracks actor ownership as soon as a spawn succeeds, and verifies cleanup before a new session starts. Timeouts need named stages and a finite terminal outcome. A session can hold a world across campaign rows while a fresh SUMO instance uses a new clock origin.
- The frame buffer will join CARLA snapshots, radar scans and delayed camera images by frame ID, with bounded backlog and explicit missing-data reasons. Advance frames while older GPU data is pending. A bounded end-of-run policy must account for delayed camera frames and keep campaign recording boundaries intact. [CARLA 0.9.16 synchrony and sensor latency](https://carla.readthedocs.io/en/0.9.16/adv_synchrony_timestep/#using-synchronous-mode)
- Existing writers and labelers define the dataset contract. Measure latency and throughput under the same seed and rig configuration, then tune queue capacities and writer concurrency when measurements justify it. Verify the effective SUMO step and CARLA fixed delta at startup, especially for requested rates whose periods may be rounded differently by the two simulators.
