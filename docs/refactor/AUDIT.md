# ScaleSense co-simulation audit

Reviewed 2026-11-26 at legacy revision `98a4744`. The checkout was clean before switching from `main` to `refactor/cosimulation-v2`.

## Repository and runtime

The repository inventory covers the CLI and Tk interfaces, `fusion/` orchestration and campaign control, `traffic/` scenario generation, map conversion and validation, `dataset/` standalone simulation, rig, capture, labeling and analysis, and the PointNet pipeline. The simulator audit traces executable paths and call sites across the checkout. Generated map geometry, notebooks, and sample media were treated as data inputs and outputs.

The shipped Windows virtual environment imports CARLA Python API **0.9.16** and runs Eclipse SUMO **1.28.0** with TraCI and sumolib **1.28.0**, on Python **3.12.10**. CARLA RPC on `127.0.0.1:2000` timed out during the initial audit, so server settings, actor behavior, camera latency, and reported freezes were assessed from source. The local distribution includes the official SUMO bridge under `Co-Simulation/Sumo`. The branch preserves `98a4744` as the legacy reference.

Inside a fused run, the capture main thread owns CARLA settings, tick calls and sensor watchdogs. CARLA's streaming callbacks deliver radar, camera and world snapshots. Capture uses a radar consumer, an actor-frame logger, a camera metadata worker, and a PNG encoder pool. The camera metadata and radar-labeling paths can consult CARLA geometry when cached metadata is incomplete. The sensor-rig child independently spawns and destroys the sensors. The runner's main thread owns TraCI and CARLA mirroring. Its headless SUMO preflight is a separate process, as is the long-lived SUMO or SUMO GUI instance. Additional standalone simulator clients include the BEV monitor's radar listeners, the labeling-test callbacks and executor, and the CARLA-only vehicle stop workers. The traffic GUI streams runner output and can escalate its shutdown from worker threads.

## Confirmed from source

| Finding | Consequence and evidence |
| --- | --- |
| The legacy fusion loop has no barrier after a CARLA tick. | The runner waits for frame F, advances SUMO and sends actor updates after F. Capture independently advances again without an acknowledgement. The runner keeps no queue of missed frames and validates neither duplicates nor gaps. Equal step lengths alone cannot prove which SUMO state CARLA rendered. Vehicle updates use unacknowledged `apply_batch`. [Runner loop](../../traffic/runner.py#L1103) · [Capture loop](../../dataset/capture/CaptureRadarCameraData.py#L2998) · [Mirror update](../../traffic/carla_sync.py#L467) |
| A single fused run can report success after the SUMO runner exits early. | Only the capture exit code determines success after startup, and the output directory comes from a shared pointer which may already exist. Capture's single-run duration uses a wall-clock deadline, so actual simulated duration varies under load. [Orchestrator](../../fusion/orchestrator.py#L311) · [Capture duration](../../dataset/capture/CaptureRadarCameraData.py#L2985) |
| A campaign's first frame is observational, and its stop path has gaps. | The runner reports the CARLA frame it observed *before* advancing SUMO and applying mirrors. The parent can count reaching the initially requested end as completion before confirming the capture accepted the window. Emergency shutdown writes `runner_final.stop` whereas the active child polls its own per-row path. After a tick timeout, stop-file polling is still keyed to the step count, which only increments on a successful step. [Campaign window and teardown](../../fusion/campaign.py#L474) · [Runner status and stop polling](../../traffic/runner.py#L1099) |
| Initialization and cleanup can lose ownership records. | Runner config, TraCI startup and controller initialization precede its main cleanup block. Within cleanup, a controller exception can prevent later cleanup. A mirror is inserted into the registry after `set_simulate_physics(False)`. Failure between spawn and insertion leaves it untracked. Destruction increments counters even when `destroy()` returns false and drops the mapping after exceptions. Final sweeps target actor types broadly, including unrelated traffic. [Runner lifecycle](../../traffic/runner.py#L1051) · [Vehicle spawn and destruction](../../traffic/carla_sync.py#L731) · [Walker spawn and destruction](../../traffic/carla_sync.py#L1057) |
| Fixed SUMO seed does not establish full reproducibility. | The seed is passed to route generation and SUMO. [Runner setup](../../traffic/runner.py#L971) · [Walker selection](../../traffic/carla_sync.py#L1047) |

## Actor geometry, sensor frames and recovery

- The mirror holds separate SUMO-ID-to-CARLA-actor dictionaries for vehicles and pedestrians. Culling changes which SUMO identities have a CARLA representation. Geometry includes map-specific offsets, handedness/yaw conversion, ground placement, junction exceptions and sidewalk projection. Offset math is duplicated in render culling. Keep these rules and blueprint classification under parity tests before extracting or changing them. [Mirror transform](../../traffic/carla_sync.py#L255) · [Vehicle placement](../../traffic/carla_sync.py#L668) · [Pedestrian placement](../../traffic/carla_sync.py#L955)
- Ground-truth capture already uses CARLA frame IDs. `TickActorSnapshotter` indexes world snapshots by frame, logs to `actor_frames.jsonl`, and evicts older frames. Radar rows carry `measurement.frame`, and fast capture joins the actor log during offline labeling. Camera metadata matches `image.frame`, waits up to 50 ms on the writer for its snapshot, then saves an image with empty actor fields if the snapshot is missing. Campaign gating accepts or rejects each callback by that callback's own frame ID. The capture has no shared completeness ledger across modalities. [Actor snapshot cache](../../dataset/capture/actor_frame_log.py#L209) · [Camera metadata](../../dataset/capture/CaptureRadarCameraData.py#L2349) · [Campaign gate](../../dataset/capture/campaign_control.py#L107)
- Output compatibility includes existing radar and camera CSVs, camera PNG paths, actor frame JSONL, segment metadata and exported radar/camera extrinsics. Labeling tools and PointNet use these artifacts. Keep 4, 8, 12 and 14 radars in the regression matrix. Both capture modes already use asynchronous writers for major work, so frame alignment can be improved without replacing the export schemas. [Capture data](../../README.md#data-capture) · [PointNet inputs](../../pointnet/README.md#1-build-the-fused-frames-once-per-capture-no-gpu)
- Duplicated lifecycle code includes runner command construction, capture launch environment, startup/cleanup sequencing, and JSON handoff between campaign and capture. Keep standalone scenario validation and labeling entry points until their behavior is covered by regression tests. [Single-run launch](../../fusion/orchestrator.py#L199) · [Campaign launch](../../fusion/campaign.py#L270)
- Suspected runtime effects to reproduce include skipped CARLA frames during slow TraCI or mirror RPCs, unreported image/metadata loss from callback lag and queue backlog, stale sensor actors after forced shutdown, and orphaned SUMO child processes on Windows. The source exposes the failure paths, but the audit did not reproduce a live simulator deadlock or establish its frequency. In particular, capture catches a failed tick and continues, the passive runner retries tick timeouts, and campaign recording has no no-progress deadline while both child processes remain alive. [Capture tick handling](../../dataset/capture/CaptureRadarCameraData.py#L3008) · [Runner timeout](../../traffic/runner.py#L1107) · [Campaign recording loop](../../fusion/campaign.py#L493)

## Live verification in Step 2

The offscreen test server reported the same CARLA build as the installed client and ran `Town10HD_Opt`. The v2 clock path adds one explicit CARLA tick and one private TraCI step. Live tests verified restoration of CARLA settings and exit of the owned SUMO process on normal completion, an injected startup failure and interruption. These checks cover the new standalone session. The legacy capture freeze, GPU sensor latency and campaign restart paths still require separate live verification. [Verification log](PROGRESS.md#2026-11-26--step-2)

## Actor and signal findings in Step 3

CARLA and SUMO use different identifiers for corridor signals. Mapping the physical heads required checking the live stop waypoints against SUMO's controlled approaches. Corresponding waypoints were within 6.3 m of the sampled SUMO lane ends, including CARLA landmark 951 on road 16 and SUMO approach 15. CARLA exposes approach colors, while SUMO can assign separate states to turn and pedestrian movements. A separate CARLA frame may be required before its actor list reflects a newly committed spawn. The v2 mirror uses session tags to recover those actors if CARLA committed a spawn whose response was lost. [Architecture](ARCHITECTURE.md#scenario-actor-and-signal-synchronization)

## Sensor findings in Step 4

The 600-frame v2 reference run received camera callbacks up to one confirmed frame later than their measurement frame. Every recorded camera and radar frame still joined to its own actor snapshot. The run exercised only one machine and one scenario. Sensor delay and completeness can vary with rendering load and storage speed. A 48-frame traffic run produced valid files and zero missing actor frames during labeling, but no matched radar returns. The existing postprocessor requires matched returns to calibrate RCS. [Verification log](PROGRESS.md#2026-11-26--step-4)

## Matched capture findings in Step 6

The Windows benchmark reproduced two legacy lifecycle problems on the pinned `98a4744` revision and on the current legacy engine. The passive traffic runner missed recorded CARLA frames, and the campaign returned with its radar and camera actors still present. The v2 campaign verified one traffic update per recorded frame and released all of its actors. Both engines delivered their expected sensor samples in these short runs. The v2 writer queue frequently reached capacity, so steady-state recording throughput remains a rollout condition. [Benchmark results](BENCHMARK.md)

## Full-rate radar output findings in Step 8

At 14 radars and 15,000 rays/s, the original v2 radar CSV stage spent 37.8 ms per frame preparing rows and 30.5 ms serializing and writing them at the median. Reusing scan-level fields and batching writes brought the median radar stage to 14.6 ms. The observed speedup covers one scenario on one host. [Full-rate recording profile](BENCHMARK.md#batched-radar-csv-follow-up)

## Full-rate campaign findings in Step 9

Two consecutive 14-radar, three-row campaigns recorded all 7,200 expected paired frames across the two runs. Every radar scan matched its sensor and frame in the written CSV. Row boundaries preserved one rig, reset SUMO time, and kept dynamic actors from earlier rows out of later recordings. Total radar return counts differed by 229 across the two runs, with complete sensor coverage in both. Heavy Demand exceeded the 50 ms tick budget at p95 on the test host. [Multi-row benchmark](BENCHMARK.md#repeated-full-rate-campaigns)

## Rollout findings in Step 10

Short S10 plans exposed a route-template error. Truncating the run to seven seconds placed the end of its delayed fast flows before their 20-second start. The route builder now omits flows whose starts fall after the run horizon. The 11-scenario launch check passed after the fix.

On the test server, changing the fixed delta could leave the first returned tick frame one behind the world snapshot. At 25 and 50 Hz, direct CARLA checks also observed two-frame advances on individual tick calls after the initial setting change. The v2 adapter now confirms two consecutive ticks before establishing the paired clock. The default stays at the verified 20 Hz.

Both legacy CLI launches still left their five rig sensors on Windows. The smoke test cleared those sensors on the isolated server. [Rollout verification](PROGRESS.md#2026-11-27--step-10)

## Endurance finding in Step 11

The S01 full-rate run stopped at the first missing actor snapshot. Walker 52 was present in every saved ground-truth frame through 25773. A traffic-only replay reproduced the disappearance at paired step 4967. The [actor mirror](../../fusion/actor_mirror.py) checks for missing actors against the preceding snapshot before applying the transform batch. This walker's disappearance became visible after the tick, when [capture](../../fusion/capture_session.py) requires every registered mirror to be present in the new snapshot.

Controlled replays isolated CARLA's walker death behavior. The [walker blueprint helper](../../traffic/carla_sync.py) set `is_invincible=false`. The baseline walker first diverged from its commanded position beside stopped car `EB_freeflow.31` at 238.35 s and left the snapshot exactly 10 s later while SUMO still tracked it. That interval matches CARLA's walker death lifespan. In separate controls, changing only this walker's invincibility and moving only this car clear both preserved the walker through 256 s. Swept actor clearance then kept the walker alive through the full S01 window. [CARLA 0.9.16 walker source](https://github.com/carla-simulator/carla/blob/0.9.16/Unreal/CarlaUE4/Plugins/Carla/Source/Carla/Walker/WalkerBase.h#L20-L32) · [Endurance verification](PROGRESS.md#2026-11-27--step-11)

Destroying a still-listening 14-radar rig could trip CARLA 0.9.16's `MultiStreamState::DisconnectSession` assert about 24 s after campaign finalization. Stopping listeners, draining 0.4 s, then destroying the actors kept the same offscreen server alive through repeated short captures and two full 11-scenario campaigns. [Stream teardown workaround](PROGRESS.md#2026-11-28--step-11-closed)
